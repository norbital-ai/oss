# Controller surfaces

Multi-entity, effective-dated pages without leaking system identifiers.

- **Minimal files & reactivity:** inline one-off lookups, pickers and `—` fallbacks; extract `.svelte` only for reusable interactive components. Hold inputs in `$state` and capture reads/derivations in `$derived` (check `current`/`error`/`loading`; no `$effect` query wiring; never mount per-row lookups — see [data-access.md](data-access.md)).
- **Identifiers & forms:** rely on `record_label` (UUID fallback; `—` when unresolved; never duplicate into a field or paint raw IDs). Relation columns and pickers resolve target labels automatically. Update `Form` requires `id={record.id}` (shares enclosing `RecordShell` draft/Save; create omits `id`). Custom `bolt.act` buttons distinguish `committed` from `pending_approval`, block transitions while dirty, keep refused edits in draft, and return `use_record_controller()?.current` to view after a committed transition.
- **Kinds on views:** `Show`/`Field` format by kind; `Board` cards ≤4 fields; `cell` snippets are for composite display only (`{ row, value }`). Model `Table` pages by cursor — never pass a whole model as a local array.
- **Entity & date scope:** multi-entity groups share one group-owned live read (`*.svelte.ts`) + header `Picker` defaulting to the first in-force row in `$derived` (loading ≠ empty; cross-entity overviews show counts per entity, never mixed time series). Every sibling page/tab in that group reads the same scope, filters its `Table`/`Board` with `where`, and opens `RecordShell mode="create"` with the scope FK in `values` (never leave one tab unscoped on `toolbar={{ new: true }}`). Inside `+representation.svelte`, hide the pre-scoped parent FK when present in `view.values` or `record`, lock cell-fixed context keys (`employment_id`, `work_date`), and filter dependent relation `<Picker>` controls with `where` to that parent. Effective-dated lists open active-only via editable `initial_filter` (`contains` `ctx.clock('day').today`), not a fixed `where`.
- **One home per model:** Settings for reusable config, operational apps for records, parent records for owned values — never mount the same model's `Table` in two apps. Use `ChildGrid` for nested child operations (parent write layer authorizes without standalone child grants).
