# Internationalization

Every tenant workspace is internationalized by contract — English is the source of truth and
Simplified Chinese ships beside it. This is not optional and does not depend on whether the tenant
"supports" Chinese today: the catalogs are bilingual from the first commit, and the compiler enforces
the wiring statically.

The platform catalogs (`@norbital-ai/ui/i18n` for the component library, `@norbital-ai/bolt/i18n` for
bolt chrome) ship with the runtime; the workspace supplies its own copy for both locales and may
override any platform key.

## Authored files

```text
src/
└── i18n/
    ├── messages.en.json   # required — your English copy
    └── messages.zh.json   # required — your Chinese copy — exact same keys
```

- Flat key → string maps, dot-namespaced. No nesting, no arrays.
- Both files are **required**. A workspace without `src/i18n/` is a structural error. When the
  tenant's market is English-only today, `messages.zh.json` mirrors the English strings — the key set
  stays identical, so the wiring is ready the day a translation arrives.
- The compiler enforces: both files present together, exactly the same key set, JSON values all
  strings, and nothing else in `src/i18n/`. A mismatch is a structural error — fix it before `bolt
sync` will pass.
- The build-time merge is `platform catalogs ← your JSON`: same keys win.

## Using it in app files

```svelte
<script lang="ts">
	import { useI18n } from '@norbital-ai/ui/i18n';
	import type { TenantI18nKeys } from '$bolt/i18n-keys';
	import { PageHeader } from '@norbital-ai/ui/page-header';

	const { t } = useI18n<TenantI18nKeys>();
</script>

<PageHeader title={t('app.quotes.header_title')} description={t('app.quotes.header_description')} />
```

- Every UI component receives internationalization objects: pass `t('key')` (and
  `{t('key', vars)}` for placeholders) as component props and snippet bodies. Never pass a raw
  string literal that a user can see.
- `TenantI18nKeys` is generated by `bolt sync` from your `messages.en.json` — unknown keys are
  compile errors, so a typo in either direction fails the build.
- Placeholders: `t('component.doc_no', { no: 'Q-2026-014' })` for a message containing `{no}`.
- `useI18n` returns `{ locale, intlLocale, t, has, setLocale }`. `t` is reactive — a locale switch
  re-renders the subtree, so plain `{t('key')}` in markup is enough; derive composite display
  strings with `$derived`, never `$effect`.
- For dynamic label fallbacks use `has(key)`: `i18n.has(key) ? i18n.t(key) : fallback`.
- The workspace shell mounts a language toggle in the sidebar (next to the theme toggle). A viewer
  switches `en` ↔ `zh` in place; the choice persists and the whole subtree re-renders.

## The raw-text rule (statically enforced)

The compiler scans every authored `.svelte` app file and flags user-facing text that is not routed
through `t(...)`:

- A text node in markup that contains a word character (e.g. `<p>Track and resolve RFIs.</p>`,
  `<Button>Save</Button>`) is a structural error — the string must come from the catalog.
- A quoted string literal passed to a component prop or snippet on a line that contains a rendered
  child (e.g. `title="Requests"`, `description="..."`) is a structural error when the value is
  not a `t(...)` call or an expression (`{...}`).

These are errors, not warnings: a raw string is a missing catalog entry by definition, so the
diagnostic names the string and points at the file and line. Fix it by adding the key to both
catalogs and referencing it with `t(...)`.

### What the rule does not flag

- `<svelte:head>` `<title>` / `<meta name="description">`: the compiler reads these for app
  identity and requires static literals. Localize the sidebar label instead with an
  `app.<appId>.title` key (the shell resolves it per locale, falling back to the metadata).
- Decorative-only text (`aria-hidden` elements), `alt` attributes on media, placeholder/mock
  strings in scripts, comments, and attributes with no rendered output.
- Collection and field labels in `+model.ts`: authored single-language (the tenant's data
  semantics). Do not move them into catalogs.
- Seed data, log messages, `error.message` payloads, identifiers, URLs.

## Key conventions

- `app.<appId>.title` / `app.<appId>.description` — one per app; `app.<groupId>.title` for groups.
- `app.<appId>.header_title`, `app.<appId>.header_description`, `app.<appId>.tab_<name>`,
  `app.<appId>.eyebrow` — PageHeader and tab copy.
- `component.<name>` — shared labels authored once and reused across apps, filters, forms.
- Keep `{placeholders}` intact and in the same position in both languages; use `{count}` + `{s}`
  for plurals (`component.employment_count` pattern).
- Reuse a platform key (`common.save`, `table.emptyState`) instead of duplicating it in your
  catalog when the meaning matches.

## Locale resolution

Stored choice (`norbital.locale`) → browser languages → English. Formatting follows the locale:
`en-US` / `zh-CN` for `Intl.*`. Server-rendered surfaces (identity pages, email) resolve from
`?lang=` then `Accept-Language`; the catalog runtime lives in
`packages/std/src/i18n/` in the OSS repository.
